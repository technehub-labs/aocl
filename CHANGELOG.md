## [0.1.4] — 2026-11-22

### Added

- **AOCL-CR-012 drafted and implemented** (State-Based Simulation Engine — quantitative evolution over the CR-010 contract): the CR document (`docs/architecture/AOCL-CR-012.md`, Proposed — engine-conformance rules SBE-001..020), the verbatim extraction of the sim-canvas prototype's physics into the canonical core `src/aocl/simcore.py` (`tools/sim_check.py` is now a shim over it with byte-identical output; `site/sim.js` remains the JS parity port), `src/aocl/engine_statebased.py` + `aocl-engine-statebased` CLI, the migrated sim-canvas scenario library (`examples/scenario-library-sim.yaml`), the StateBased reference execution definition (`examples/execution-definition-statebased-sim.yaml`), and the committed reference run summary (`examples/statebased-run-summary.json`). The engine is conformance-gated (execution definition state-based readiness, valid scenario library, canonical loop with assessment vectors as the policy source), runs the full invariant suite (S1–S8 with the multi-seed S6 study) with each invariant reported as a **first-class run verdict** and the formal-model findings (F1–F4) as observations, and emits SimulationEvidence carrying run identity, seed, vectors and engine version. Reference run: 7/7 invariants hold as verdicts under the canonical loop's vectors.


### Added

- **AOCL-CR-011 drafted and implemented** (Logical Simulation Engine — the first engine implementing the CR-010 contract): the CR document (`docs/architecture/AOCL-CR-011.md`, Proposed — engine-conformance rules LSE-001..022), `src/aocl/engine_logical.py` + `aocl-engine-logical` CLI, the Logical-mode reference execution definition (`examples/execution-definition-logical.yaml`), and the committed reference run summary (`examples/logical-run-summary.json`). The engine is **conformance-gated** (it refuses to execute any artifact that fails its native validator) and enforces the CR-010 semantics at runtime: separated actual/observed/estimated channels with controller-visibility enforcement (a disturbance declared unknown to the Controller never reaches the controller view until an observation copies it), graph-faithful activation with WaitForAll synchronization gating, branch-first condition evaluation with unresolved conditions recorded (never defaulted), approval suspension with declared timeout windows and escalation targets, the five-record dispatch chain (an acknowledgement never advances state; a Failed execution hands continuation to the exception path), safe states recorded with pending verification, deterministic seeded runs with input-derived run identity, and SimulationEvidence carrying run/scenario/seed/engine identity. The integration proof runs the full example family end to end: the granted-approval run completes VerifiedCompletion in 3 ticks; the default run escalates to SafeStateTransition after the declared approval timeout, with verification honestly pending. Numeric semantics are a declared non-normative reference interpretation pending CR-012's quantitative engine.


### Added

- **AOCL-CR-010 baselined and implemented** (canonical execution semantics — the Modeling-stage → engine transition): the CR document (`docs/architecture/AOCL-CR-010.md`, Proposed — principles P27–P34, rules EXE-001..040, decisions AD-010-01..12), `schema/execution-semantics.schema.json` (the ExecutionDefinition contract), `src/aocl/execution.py` + `aocl-execution` CLI (native validation with the §17 profiles and mode-specific **engine readiness** — logical vs state-based), and the validated reference instance (`examples/execution-definition.yaml`). The ExecutionInstance binds a behavioral specification, a simulation scenario and the control/evidence models into a runnable interpretation whose every semantic decision is a declared policy: graph-faithful activation, guards-before-effects, always-checked authority, blocking freshness, deterministic tie-breaking, the CR-007 dispatch chain as distinct records, suspending approval gates, escalating exception handling, verified safe states, seeded determinism — and runtime **information-visibility enforcement** (`controllerVisiblePolicy: PerScenarioDeclaration` is the only conforming value; `Full` is forbidden): the simulated Controller never receives the scenario's hidden ground truth, which is what makes the veracity experiments valid. The §19 migration carries the simulation canvas's implicit policies into a Draft ExecutionDefinition as carried semantics, never promoted. No engine is implemented; CR-011/012 now have a normative contract to implement against.


## [0.1.3] — 2026-11-07

### Added

- **CR-009 implementation tranche delivered** (simulation scenario and disturbance model — completes the Modeling stage): `schema/scenario.schema.json` (the ScenarioLibrary contract), `src/aocl/scenario.py` + `aocl-scenario` CLI (native validation implementing SCN-001..057 with the ten conformance profiles of §21 plus **mode-specific simulation readiness** — logical vs state-based reported separately per AD-009-15), and the validated reference instance (`examples/scenario-library.yaml` — the §23 congestion-and-recovery scenario with the stale-telemetry and competing-loops variants, acceptance criteria 27–28). Enforced, not just representable: actual/observed/estimated initial states stay distinct (SCN-011/AD-009-04); initialization without silent defaults (SCN-013); **every disturbance declares what the simulated Controller may know about it** (SCN-027/§11.5); event dependency cycles detected (SCN-034); parameters range-checked (SCN-015); stochastic scenarios declare their randomization basis (SCN-049); external datasets need stable snapshots (SCN-050); Incompatible scenarios can never be silently Approved (SCN-053). The §24 migration surfaces the simulation canvas's engine-embedded scenario data (`model/behavior.yaml`: four scenarios, disturbances, invariants) as Draft skeletons with the hard-coding inventoried — the canvas's scenarios now have a canonical home.

- **CR-008 implementation tranche delivered** (verification and evidence model): `schema/evidence-model.schema.json` (the EvidenceModel contract), `src/aocl/evidence_model.py` + `aocl-evidence` CLI (native validation implementing VER-001..050 with the nine conformance profiles of §19 reported separately), and the validated reference instance (`examples/evidence-model.yaml` — the §21 network-assurance evidence chain, acceptance criteria 22–23). Enforced, not just representable: execution evidence never establishes an operational outcome and transition claims require established-state evidence rather than the command that requested the transition (VER-034/036, AD-008-07); Failed, Inconclusive and Conflicting remain distinct governed outcomes with evidence conflicts preserved unresolved (VER-024, AD-008-08/10); self-verification is honestly labeled and safety/regulatory-critical claims require independent assurance (VER-029/030); simulation evidence carries run/scenario/seed/engine identity and never substitutes for operational evidence (VER-039..042, AD-008-11); positive results require identifiable evidence, dispositions never overwrite original results, and incomplete chains are reported explicitly (VER-014/017/050). The §22 migration carries control-model verification references into Draft skeletons and deliberately does NOT import assessment or realization scores as evidence records (AD-008-13).

- **CR-007 implementation tranche delivered** (control contracts and state transitions): `schema/control-contract.schema.json` (the ControlModel contract), `src/aocl/control_contract.py` + `aocl-control-contract` CLI (native validation implementing CTM-001..040 with the seven conformance profiles of §19 reported separately and simulation readiness assessed independently per AD-007-12), and the validated reference instance (`examples/control-contract.yaml` — the §17 network-assurance example, acceptance criterion 21). Enforced, not just representable: the six-way state distinction with estimator-named estimates (CTM-008/012), authority never inferred from relationships (CTM-028) with explicit coordination required for overlapping control scopes (CTM-029), execution-completion ≠ operational-outcome via evidential-strength matching of postcondition claims against their supporting signals (AD-007-09 — acknowledgement does not establish execution, execution status does not establish plant state), safety/regulatory invariants binding on any contract touching a covered variable (CTM-033), and unit compatibility (CTM-006). §21 migration carries goal reference conditions into Draft skeletons and deliberately does NOT convert controlled-system bindings into authority.

## [0.1.2] — 2026-11-07

### Added

- **CR-006 implementation tranche — the canonical behavioral specification** (the first Modeling-stack tranche): `schema/behavioral-spec.schema.json` (the BehavioralSpecification contract), `src/aocl/behavior_spec.py` + the new **`aocl-behavior-spec`** CLI (native validation implementing BSS-001..036 with the four conformance levels of §17 — schema / structural / behavioral / simulation readiness — reported separately per BSS-035/036), and the validated reference instance (`examples/behavioral-spec.yaml`) demonstrating all eight behavioral patterns (A–H) of §19. The specification carries the **E/C/V_d measurement anchors** as validated structure (human participation = E, control-architecture/fusion declarations = C, observation-quality declarations = V_d), enforces the authority rule (an Action without an AuthorizedBy reference is invalid) and governed learning (recording is free; policy change requires authorization), and migrates loop registrations to Draft skeletons with gaps inventoried, never fabricated.
- **CR-002 implementation tranche — the canonical closed-loop metamodel**: `schema/canonical-loop.schema.json` (the canonical ClosedLoop contract), `src/aocl/metamodel.py` + **`aocl-metamodel`** CLI (structural + semantic validation implementing MM-001..018, lifecycle-vs-runtime separation, the ADR-006 aggregation-binding rule — vectors first-class, level derived — and modeler→canonical migration per §11), and the validated illustrative instance (`examples/canonical-loop.yaml`).
- **Cost-benefit calibration and planning tools** (`aocl-realization`): `--calibrate` fits your own cumulative cost-per-level points against linear, logarithmic and exponential shapes and reports the supported shape with fit quality; `--plan` projects the L1–L5 cost/benefit curve against a budget and reports the highest reachable level plus marginal value-per-cost per transition; `--chart` renders the projection as SVG (`aocl.planchart`, no dependencies). No cost constants are baked in — the reference-scenario multiples (including the 7× L4→L5 illustration) are labeled as such and used only as explicit uncalibrated fallbacks. The same planner is ported to the site engine and pinned to Python parity (`tests/sim-parity.json` planner cases).
- **Architecture baseline committed** ([ADR-006](docs/decisions/adr-006-simulation-evidence-and-architecture-alignment.md)): AOCL-ARCH-001 (normative foundation — 7-stage behavioral lifecycle, hybrid simulation, P01–P12), AOCL-CR-001 (adoption CR), and the preceding architectural review, under `docs/architecture/`. The simulation is designated the prototype of ARCH-001's state-based simulation mode; findings F1–F4 are disposed against the CR sequence (F1 aggregation-binding → must-resolve in CR-002).
- **Modeling tranche queued** ([docs/architecture/](docs/architecture/README.md)): AOCL-CR-003 (behavioral lifecycle), CR-004 (control architecture), CR-005 (relationships, constraints, composition — with the new principles P13–P18), CR-006 (behavioral specification schema — P19–P26), CR-007 (control contracts and state transitions), CR-008 (verification and evidence), CR-009 (simulation scenarios and disturbances — completes the Modeling stage). The engine tranche (CR-010..013) is sequenced after Modeling approval.
- **AOCL-CR-002 queued** ([docs/architecture/AOCL-CR-002.md](docs/architecture/AOCL-CR-002.md)): Canonical Closed-Loop Metamodel — carrying the ADR-006 dispositions (§4a): the aggregation-binding rule (F1) as must-resolve, velocity-fit fields (F4), and experimentation containment (F3).
- **Simulation canvas** (`site/simulation.html`, `site/sim.js`): deterministic discrete-event simulation testing the level→policy mapping — vector-driven semantics (GD goals, DV observation quality incl. wrong-direction actions, FI learning), playbook pre-emption, novel containment, sandboxed experimentation, humans by HITL/HOTL/HOOTL, governance (exception upflow → playbook conversion). Parity-verified against the Python engine.
- **Batch invariant runner** (`tools/sim_check.py`): 7 plausibility invariants (restoration monotonicity, burden collapse, novel-mode discriminator, velocity orthogonality, sandboxing, policy downflow, veracity multiplier) + 4 formal-model findings — all 7 hold at the default seed; run in CI.
- **`model/behavior.yaml`** — the behavioral semantics under test (informative), and **`docs/simulation.md`** — the findings report.

### Changed

- **ADR-007 — realization promoted to the core decision instrument** ([docs/decisions/adr-007-realization-cost-benefit-instrument.md](docs/decisions/adr-007-realization-cost-benefit-instrument.md)): the cost-benefit thesis (exponential realization effort, diminishing incremental gains, the L3–L4 inflection) is articulated as the organizing premise; `aocl-realization --decide` ships the marginal effort-vs-value decision table with the L3→L4 inflection gate; the L3 investment gate governs L4–L5 tooling and investment. Informative status preserved for uncalibrated use. **Refined with calibration primacy:** the exponential-cost pattern was observed in one controlled research scenario — it demonstrates costs *can* grow exponentially, it does not constrain every domain to that shape; the tool now helps organizations discover which shape applies to them rather than assume one.
- **Research framing (breaking for external attribution):** Closed Loop Automation and Autonomous Operations are now stated as first-class concepts established through the AOCL foundational research corpus — all external registry citations have been paraphrased away across docs, model provenance, NOTICE, and packaging metadata. The concepts stand on the programme's own research.

## [0.1.0] — 2026-11-05

### Added (initial release)

- **Loop maturity assessment**: L1–L5 ladder across three vectors (Goal Decisioning, Data Veracity, Feedback Intelligence), weakest-link aggregation, frontier + barrier guidance, decision-model (OODA/MAPE) and HITL recommendations — `aocl-score`.
- **Realization model (informative heuristic)**: R = √(E² + (C·V_d)²) with four-vector E/C decompositions, effort e^R, sensitivity partials, inverse solvers, Table 1.1 reference points, and the logarithmic/exponential value models — `aocl-realization`.
- **Loop ledger** (schema 1): registry of managed closed loops with validity checks, guardrail hygiene (L3+ requires guardrails), review staleness, and portfolio shape — `aocl-ledger`.
- **Loop modeler model**: entities (process/capability/system/function) + loops specified in the CLAM-aligned format (Closed-Loop-Management data model 1.0), with `aocl-clam-export` provisioning payloads — `aocl-model --clam`.
- **Interactive site** (offline-first, no build step): assessment quiz + scorecard + vector radar; realization sliders driving the E–C plane, realization sigmoid, and effort curve; **Loop Modeler** (visual lanes for processes/capabilities/systems/functions, loop chips, full CLAM-shaped loop editor, live portfolio scatter); portfolio + latency-budget views. Parity-tested against the Python engine via the golden corpus.
- **Golden corpus**: 16 exact-output cases (7 assessment, 9 realization incl. the source document's worked examples) run against both engines in CI; cross-grepped RULESET_VERSION parity; drift blocks release.
- **Framework documentation**: 14 docs formalizing the AOCL research corpus guide (v1.2.0) — framework, maturity model, assessment, realization model, loop velocity, decision models, loop modeler, CLAM alignment, value streams, use cases, AO-ready assumptions, AOMM mapping, ledger format, versioning, naming, limitations.
- **Figures**: 12 recreated SVG figures + the 17 originals archived with provenance (incl. the Fig. 7 toolbar-artifact note).
- **Pipelines**: CI (Python self-tests + corpus + JS self-test + corpus + schema validation + docs link check), GitHub Pages (gated on site self-test), release (wheel + sdist smoke, PyInstaller binaries for macOS arm64 / Linux x86_64 / Windows x86_64, changelog-extracted notes, SHA256SUMS), manual PyPI trusted publishing.
